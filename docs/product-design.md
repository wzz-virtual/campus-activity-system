## 1. 产品概述

### 1.1 背景与问题

校园活动目前靠「群通知 + 在线表格」组织，这套办法在活动数量少的时候能用，一旦多起来就会暴露四个问题：

| 问题 | 具体表现 |
| --- | --- |
| **名额管不住** | 表格靠人肉盯，抢跑、重复填、超员是常态。「限额 100 结果来了 103 人」几乎每次都会发生 |
| **信息散** | 活动散落在几十个群里，学生不知道有什么活动，只能被动等转发 |
| **到了才算数** | 报名人数不等于到场人数。没有签到，主办方无法回答「到底来了多少人」 |
| **复盘无据** | 谁批的活动、什么时候被驳回、改了哪一版，全靠记忆和聊天记录 |

### 1.2 产品定位

> **一句话定位**：把校园活动从「群通知 + 在线表格」搬到线上，跑通一条可追溯的闭环——
> **组织者发布 → 学生浏览报名 → 现场签到 → 统计复盘**。

产品的价值不在于功能多，而在于**这条闭环不能断**。任何一个环节断了（比如报了名却不知道有没有报上、到了现场签不了到），用户就会退回群里用表格。

### 1.3 度量目标

以下是**待确认的候选指标**，用于判断 MVP 是否真的解决了问题：

| 指标 | 定义 | 候选目标 | 说明 |
| --- | --- | --- | --- |
| 闭环完整率 | 线上报名人数 ÷ 线上报名+线下补录人数 | ≥ 90% | 衡量报名环节是否被真正使用 |
| 签到数据覆盖率 | 有签到记录的活动数 ÷ 已结束活动数 | ≥ 95% | 直接反映「到了才算数」是否成立 |
| 超员事件数 | 报名人数 > 人数上限 的活动数 | **0** | 硬性红线，靠并发控制保证 |
| 提前锁定率 | 在报名截止前 24h 完成报名的占比 | 观测项 | 用于评估「名单锁定」规则的影响面 |

> 具体目标值需结合学校活动总量校准，当前数值为提案。

## 2. 用户与角色

### 2.1 角色定义

系统共有三个角色，**角色只能由管理员在后台设置，用户无法自行改变或申请**。

| 角色 | 代码 | 说明 |
| --- | --- | --- |
| 学生 | `STUDENT` | 活动的主要参与者 |
| 社团 | `CLUB` | 活动的组织者，发布前须经管理员审核 |
| 校级管理员 | `ADMIN` | 平台管理者，可直接发布活动、审核社团活动 |

> 系统**不提供自助注册**。校园场景下开放注册等于任何人都能给自己开一个号，账号一律由管理员创建后发放。

### 2.2 用户画像与典型场景

**学生 —— 李明，大二**

> 「我想找点活动参加，但不知道去哪看。看到感兴趣的在群里点了报名，也不知道到底报上没有。」

- 核心诉求：**一站式看到有什么活动**、报名要当场知道结果、到场别排长队
- 典型场景：课间刷活动列表 → 挑一个时间合适的报名 → 活动当天到场签到
- 最怕的事：报名了却没报上；到了现场排长队签到

**社团 —— 摄影协会，干事小张**

> 「上次办活动，报名填了 80 个，实际来了 45 个，剩下的场地和物料全浪费了。」

- 核心诉求：**提前知道准确人数**以便备料、到场情况的准确记录
- 典型场景：创建活动 → 提交审核 → 等管理员批 → 看报名名单 → 现场核验签到 → 导出名单复盘
- 最怕的事：临门撤人导致物料浪费；活动被驳回却不知道原因

**校级管理员 —— 陈老师**

> 「社团报上来的活动，我得知道谁在发、发的是什么，出了问题要能找到人。」

- 核心诉求：**统一入口 + 有据可查**，出事能追溯到人和时间
- 典型场景：集中处理待审核活动 → 通过或驳回并写明理由 → 查看全部活动的运行情况
- 最怕的事：活动出问题时找不到负责人；审核决定没有留痕

### 2.3 权限矩阵

| 操作 | 学生 | 社团 | 管理员 |
| --- | :---: | :---: | :---: |
| 浏览活动列表 / 详情 | ✓ | ✓ | ✓ |
| 报名 / 取消报名 | ✓ | ✓ | ✓ |
| 签到（本人） | ✓ | ✓ | ✓ |
| 创建活动 | ✗ | ✓（→ 待审核） | ✓（→ 直接发布） |
| 编辑活动 | ✗ | 仅本人创建且未发布 | 全部 |
| 提交审核 | ✗ | ✓ | — |
| 审核通过 / 驳回 | ✗ | ✗ | ✓ |
| 取消活动 | ✗ | 仅本人创建 | 全部 |
| 查看报名名单 | ✗ | 仅本人创建的活动 | 全部 |
| 核验签到 | ✗ | 仅本人创建的活动 | 全部 |
| 查看统计 | ✗ | 仅本人创建的活动 | 全局 |
| 分类管理 | ✗ | ✗ | ✓ |
| 用户与角色管理 | ✗ | ✗ | ✓ |
| 处理密码找回申请 | ✗ | ✗ | ✓ |

**两条实现层面的硬性要求**（写在这里是为了防止后续开发走偏）：

1. **每个写操作都必须在服务端校验角色与归属权。** 前端把按钮藏起来不算权限控制——改一个请求就能绕过。
2. **角色永远不能来自客户端。** 角色的唯一来源是数据库里的 `user.role`。登录表单里多传一个 `role=ADMIN` 不应该有任何效果（已有测试专门验证这一点）。

## 3. 核心业务流程

### 3.1 主闭环

```
 组织者创建活动 ──> 管理员审核 ──> 学生浏览 ──> 报名 ──> 现场签到 ──> 统计复盘
                                                              │
                                                              └──> 导出名单
```

三个「关口」决定这条闭环是否可信：

| 关口 | 保障机制 |
| --- | --- |
| 发布关 | 社团活动必须过审核，管理员创建的直接发布 |
| 报名关 | 原子扣减名额 + 唯一索引，保证不超卖、不重复 |
| 签到关 | 签到信息挂在报名记录上，只有报名的人能签到 |

### 3.2 学生视角

```
登录 ──> 活动广场（筛选 / 搜索 / 翻页）
              │
              ├──> 活动详情 ──> 可报名？ ──是──> 立即报名 ──> 名额 -1，状态变为「已报名」
              │                    │
              │                    └──否──> 按钮置灰并说明原因
              │                            （名额已满 / 报名已截止 / 活动已开始 / 活动已取消）
              │
              └──> 我的报名 ──> 取消报名（受锁定规则限制，见 5.3）
                            └──> 查看签到状态（待参加 / 待签到 / 已签到 / 缺席）
```

### 3.3 社团视角

```
登录 ──> 我的活动（按状态分组：草稿 / 待审核 / 已驳回 / 已发布 / 进行中 / 已结束 / 已取消）
              │
              ├──> 新建活动 ──> 表单校验 ──> 提交审核（草稿可先存着）
              │
              ├──> 待审核 ──> 可撤回为草稿
              ├──> 已驳回 ──> 查看驳回原因 ──> 修改后重新提交
              │
              └──> 已发布 / 进行中 ──> 报名与签到
                                          ├──> 查看报名名单
                                          ├──> 勾选核验签到（实时更新签到率）
                                          ├──> 展示 6 位签到码供学生自助签到
                                          └──> 导出 CSV 名单
```

### 3.4 管理员视角

```
登录 ──> 审核中心
              ├──> 待审核队列 ──> 通过（→ 已发布，学生立即可见）
              │                └──> 驳回（必填原因，创建者可见）
              └──> 审核日志（只追加、不修改，可追溯谁在什么时候批了什么）
         ──> 全部活动 ──> 按状态筛选 ──> 强制取消
         ──> 发布活动（跳过审核，直接发布）
         ──> 用户与分类管理
```

### F1 登录与角色鉴权

**目标**：确认「你是谁」，并保证登录之后系统每次请求都记得这件事。

**主要流程**

1. 用户访问系统 → 未登录则跳转登录页
2. 输入学号 / 工号 + 密码 → 服务端校验
3. 校验通过 → 建立会话 → 按角色跳到对应首页
4. 后续每个请求由服务端还原身份，路由层校验角色

**业务规则**

| 规则 | 值 | 理由 |
| --- | --- | --- |
| 登录凭证 | 学号 / 工号 + 密码 | 不引入邮箱、手机号，减少字段和找回流程 |
| 密码存储 | 哈希存储，绝不存明文 | 数据库泄露时密码不可直接读出 |
| 密码最小长度 | 8 位 | 卡在「写入密码」的唯一入口上 |
| 失败提示 | 统一提示「学号或密码不正确」 | 区分提示会变成账号枚举工具 |
| 失败锁定 | 连续 5 次失败，锁定 15 分钟，到期自动解锁 | 抵挡撞库；锁定时间刻意取短，避免被用来把真实用户挡在门外 |
| 会话有效期 | 8 小时 | 大致等于「一天登录一次」，不给「一次登录永久有效」 |
| 会话安全 | HttpOnly + SameSite=Lax（生产环境加 Secure） | 防脚本窃取、防跨站伪造请求 |

**异常与边界**

| 情况 | 处理 |
| --- | --- |
| 账号不存在 | 与密码错误返回**完全相同**的提示和状态码，且耗时也要一致 |
| 账号被停用 | 只有密码正确时才提示「已停用」，否则一律走通用提示 |
| 处于锁定期 | 即使密码正确也拒绝，并提示剩余时间 |
| 登录前会话里有残留数据 | 登录时重建会话，防止会话固定攻击 |
| 登录后要跳转到 ?next= 指定的页面 | 只允许站内路径，`//evil.com`、`/\evil.com` 一律拒绝 |

### F2 活动创建与发布

**目标**：让组织者能快速把活动信息发布出去。

**活动字段**

| 字段 | 必填 | 说明 |
| --- | :---: | --- |
| 标题 | ✓ | 不超过 100 字 |
| 分类 | ✓ | 从已有分类中选择 |
| 封面 | ✗ | 图标 / 图片 |
| 简介 | ✗ | **纯文本**，支持换行；不做富文本编辑器 |
| 开始时间 / 结束时间 | ✓ | 结束必须晚于开始 |
| 报名截止时间 | ✓ | 必须不晚于开始时间 |
| 活动地点 | ✓ | |
| 人数上限 | ✓ | 大于 0 的整数 |

**业务规则**

- **社团创建的活动一律进「待审核」**，通过后才出现在活动广场。
- **管理员创建的活动跳过审核，直接发布。**
- 表单校验失败时**必须保留已填内容**，只提示错在哪一项。让用户从头再填一遍是最容易招致放弃的体验。
- 活动**进行中或已结束**后，核心信息（时间、地点、人数上限）不可再修改。

---

### F3 活动审核

**目标**：把住发布关，同时让审核决定有据可查。

**业务规则**

| 规则 | 说明 |
| --- | --- |
| 谁能审 | 仅校级管理员 |
| 通过 | 状态变为「已发布」，学生立即可见 |
| 驳回 | **必须填写原因**，原因展示给创建者 |
| 驳回之后 | 创建者可修改后重新提交，回到「待审核」 |
| 撤回 | 创建者可在待审核阶段撤回为草稿 |
| 留痕 | 提交 / 通过 / 驳回 / 取消全部记入审核日志，**只追加、不修改** |

**为什么驳回必须填原因**：不填原因的驳回等于让组织者猜。猜不出来就会来问，审核环节的沟通成本反而更高。

### F4 活动浏览与搜索

**目标**：学生能快速找到合适的活动。

**业务规则**

- 学生**只能看到**状态为「已发布 / 进行中 / 已结束 / 已取消」的活动。草稿、待审核、已驳回对普通学生完全不可见。
- 列表支持：分类筛选、状态筛选、标题 / 简介 / 地点关键词搜索。
- **必须分页**，不允许一次查出全表。
- 默认按开始时间倒序（最新的活动排在前面）。
- 列表卡片需直接呈现决策所需信息：**剩余名额、报名是否已截止**。不要让学生点进去才发现报不上。

---

### F5 报名与取消报名

**目标**：报得上、报得准、不超卖。

**报名的四项检查**（服务端逐项执行，前端提示只是提前告知）

| 检查 | 不通过时的提示 |
| --- | --- |
| 活动状态是「已发布」 | 该活动尚未发布 / 活动已开始，报名通道已关闭 / 该活动已取消 / 该活动已结束 |
| 当前时间早于报名截止时间 | 报名已截止 |
| 名额未满 | 名额已满 |
| 本人未报名过 | 你已经报名过这个活动了 |

**并发要求**：名额扣减必须是**数据库层面的原子操作**，禁止「先查询人数、再插入」。判断和扣减要在同一条语句里完成，靠影响行数判断成功与否。重复报名由 `(活动, 用户)` 唯一索引兜底。

> 这是整个系统最容易翻车的地方。具体 SQL 见 `mvp-design.md` 第 6.1 节。

**取消报名的规则**（这是产品的核心约束之一，见 5.3 详述）

- 距报名截止**不足 24 小时**起，名单锁定，不可再取消
- 报名截止之后同样不可取消
- 活动开始后不可取消
- 活动进行中如果**尚未开始签到**（即学生尚未签字确认到场），取消仍按上述规则处理

**为什么要有锁定**：组织者需要按稳定名单备料、排座位。临门撤人会直接影响活动执行。锁定窗口取 24 小时，是「给组织者留出准备时间」与「给学生留出反悔空间」之间的折中。

### F6 签到核验

**目标**：把「报名」变成「到场」。

**两条并行的签到通道**

| 通道 | 使用者 | 说明 |
| --- | --- | --- |
| **名单手动勾选** | 组织者 / 管理员 | 在报名名单上直接标记，最省事，适合小规模活动 |
| **6 位签到码** | 学生自助 | 活动开始时由服务端生成，学生凭码自助签到 |

> 为什么不只做一种：手动勾选在几十人的活动上很快，但几百人就会排队；签到码适合大规模，但需要提前把码展示出来。两条路都留着，组织者按活动规模自己选。

**业务规则**

- 签到信息**直接挂在报名记录上**，不单独建表（MVP 不支持「未报名直接签到」，两者一对一）。
- 只有报名记录为「已报名」的用户才能签到。
- 签到码在活动进入「进行中」时生成，活动结束后自动失效。
- 支持撤销误操作（把错误勾选的签到取消掉）。
- 签到状态对学生的呈现分为四种：**待参加 / 待签到 / 已签到 / 缺席**。

---

### F7 统计与名单导出

**目标**：回答「这场活动到底办得怎么样」。

**两个核心指标**

| 指标 | 定义 | 反映什么 |
| --- | --- | --- |
| **签到率** | 实到人数 ÷ 报名人数 | 「报名的人来了多少」——活动的实际吸引力、提醒是否到位 |
| **上座率** | 报名人数 ÷ 人数上限 | 「名额用掉了多少」——宣传是否触达了足够的人 |

> 两个指标要一起看。签到率低而上座率高，说明宣传到位但内容不吸引人；两个都低，说明宣传本身有问题。

**其他要求**

- 名单导出为 CSV，**必须带 UTF-8 BOM**，否则用 Excel 打开中文会乱码。
- 统计口径固定：报名总数包含「已取消」以外的所有报名记录；「缺席」计入报名总数但不计入实到人数。

---

### F8 分类与用户管理

- 分类由管理员维护，支持增删改；删除前需校验是否仍被活动引用。
- 用户由管理员创建，可调整角色、停用账号。
- 停用账号后该用户无法登录，但历史报名与签到记录保留。

### F9 忘记密码

**目标**：学生忘了密码时，有一条**可追溯**的找回路径，而不是只能私下去找管理员口头说一声。

**完整流程**

```
学生：登录页 →「忘记密码」→ 填学号 + 核实信息 → 提交申请
                                    │
学生：把学号报给管理员  ←───────────┘
                                    │
管理员：管理后台 → 密码找回申请 → 核实身份（当面 / 电话）
                                    │
                     ┌──────────────┴──────────────┐
                  核实通过                      核实不通过
                     │                            │
      系统生成 12 位随机临时密码              标记为「未通过」+ 备注
      并在页面上显示【一次】                        │
                     │                            │
      管理员当场/电话告知本人                    流程结束
                     │
学生：用临时密码登录 → 被强制跳转改密页 → 设置新密码 → 恢复正常使用
```

**业务规则**

| 规则 | 说明 |
| --- | --- |
| 谁能申请 | 任何人（未登录状态），只需填学号与核实信息 |
| 反馈一致性 | **无论学号是否存在，返回完全相同的提示**。这个页面没有登录页的失败次数限制，一旦能被用来试探学号是否存在，它就是一个更好用的账号枚举工具 |
| 重复提交 | 同一用户只保留一条待处理申请，避免刷满管理员队列 |
| 谁能处理 | 仅校级管理员 |
| 处理方式 | 系统生成 **12 位随机**临时密码，**只在生成时显示一次**（服务端只存哈希，无法再次查看） |
| 管理员不掌握最终密码 | 管理员只发临时密码；用户登录后被强制立即修改。这样账号仍保持「只有本人知道密码」 |
| 强制改密 | 改密之前，该账号访问**任何页面**都会被拦回改密页（仅放行改密页、登出、健康检查） |
| 改密校验 | 需验证当前（临时）密码；新密码不少于 8 位；两次输入需一致；不得与当前密码相同 |
| 留痕 | 谁在什么时候给哪个账号重置过，全部记录在案 |

> **为什么不让管理员直接指定新密码**：那样管理员就知道了用户的密码，账号失去「只有本人知道密码」这个最基本的属性，出了问题也说不清是谁在用这个账号。

> **为什么强制改密要拦在每个请求上**：只在登录那一步重定向是不够的——用户敲一下地址栏就绕过去了。

**V1.1 计划**：增加邮箱验证码自助重置，学生可自行完成，不必等管理员。
（需要配置邮件发送服务，且用户资料里必须是真实可收信的邮箱。）

## 5. 业务规则汇总

> 本节是**单一事实来源**。其他章节描述与本节冲突时，以本节为准。

### 5.1 活动状态机

```
草稿 DRAFT ──提交──> 待审核 PENDING ──通过──> 已发布 PUBLISHED ──开始──> 进行中 ONGOING ──结束──> 已结束 FINISHED
                 │                  │
                 └──驳回──> 已驳回 REJECTED（可修改后重新提交）
                                    │
                     未结束前任意阶段 ──> 已取消 CANCELED
```

管理员创建的活动**跳过 `PENDING`**，直接置为 `PUBLISHED`。

| 状态 | 说明 | 可见性 | 允许的操作 |
| --- | --- | --- | --- |
| `DRAFT` | 草稿 | 仅创建者 | 编辑、删除、提交审核 |
| `PENDING` | 待审核 | 创建者 + 管理员 | 管理员通过 / 驳回；创建者撤回 |
| `REJECTED` | 已驳回 | 创建者 + 管理员 | 创建者修改后重新提交 |
| `PUBLISHED` | 已发布，报名中 | 全员 | 报名 / 取消报名；创建者可编辑等 |
| `ONGOING` | 进行中，签到开放 | 全员 | 签到；创建者核验；**不可报名、不可取消** |
| `FINISHED` | 已结束，数据归档 | 全员（只读） | 查看统计 |
| `CANCELED` | 已取消 | 全员（只读） | — |

> **为什么先把状态定成枚举**：把「草稿」和「已发布」混在一个布尔字段里，是这类系统最常见的返工来源。状态一旦成为枚举，后续加审核节点只是加一个值，不用改存量数据。

### 5.2 报名规则

| 条件 | 是否可报名 |
| --- | :---: |
| 活动状态 ≠ `PUBLISHED` | ✗ |
| 当前时间 ≥ 报名截止时间 | ✗ |
| 报名人数 ≥ 人数上限 | ✗ |
| 本人已有报名记录 | ✗ |
| 以上都不满足 | ✓ |

### 5.3 取消报名规则

| 条件 | 是否可取消 | 提示 |
| --- | :---: | --- |
| 活动已取消 / 已结束 | ✗ | 活动已取消 / 活动已结束 |
| 活动进行中 | ✗ | 活动已开始，无法取消报名 |
| 当前时间 ≥ 报名截止时间 | ✗ | 报名已截止，名单已锁定 |
| 距报名截止不足 **24 小时** | ✗ | 距报名截止不足 24 小时，名单已锁定 |
| 活动状态为 `PUBLISHED` 且距截止 ≥ 24 小时 | ✓ | 界面提示「可取消至 MM-DD HH:mm」 |

> 这条规则同时覆盖了「截止前最后一天」和「截止之后」两种情况。
> **界面要求**：不只是在锁定后把按钮置灰，在**还能取消的时候就要把截止时刻明确写出来**，让用户知道还剩多久可以反悔。

### 5.4 签到规则

| 条件 | 是否可以签到 |
| --- | :---: |
| 活动状态 ≠ `ONGOING` | ✗ |
| 该用户没有「已报名」的记录 | ✗ |
| 凭码签到时码值不匹配 | ✗ |
| 已签到 | ✗（可撤销后重签） |

| 约定 | 说明 |
| --- | --- |
| 按钮不可用时必须说明原因 | 不能只置灰。学生看到「名额已满」「报名已截止」才知道发生了什么 |

### 6.3 交互原型

`demo/index.html` 是一份**单文件、无需后端、离线可打开**的静态原型，覆盖上述全部 8 个模块，三角色可自由切换，所有操作即时生效、刷新即重置。

原型内置「体验路线」指引，可按以下顺序走一遍完整闭环：

1. 以学生进入 → 筛选择活动 → 报名 → 观察名额变化
2. 试报「名额已满」「报名已截止」的活动，看拦截提示
3. 切到社团 → 查看各状态活动 → 新建活动并提交审核
4. 切到管理员 → 审核通过一个、驳回一个（填原因）
5. 切回社团 → 查看状态变化 → 对被驳回的活动重新提交
6. 在「报名与签到」勾选签到 → 观察签到率变化 → 导出 CSV

## 7. 非功能需求

### 7.1 安全

| 项 | 要求 | 当前状态 |
| --- | --- | --- |
| 密码存储 | 哈希存储，不可逆 | ✅ |
| 密码强度 | 最小 8 位，卡在唯一写入点 | ✅ |
| 会话 | 签名 Cookie，HttpOnly + SameSite；生产加 Secure；8 小时有效期 | ✅ |
| CSRF | 全局校验 token，覆盖所有写操作 | ✅ |
| 登录防爆破 | 连续失败锁定 + 时序抹平（防账号枚举） | ✅ |
| 开放重定向 | `?next=` 只允许站内路径 | ✅ |
| 越权 | 每个写操作在服务端校验角色与归属权 | ✅ 全部业务接口已接入 |
| 生产配置自检 | 缺密钥 / 密钥过短 / 用开发占位值 → 拒绝启动 | ✅ |
| 响应头 | `X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy` | ✅ |
| 并发 | 报名名额原子扣减，绝不超卖 | ✅ 40 线程抢 25 名额的压测通过 |
| 前端资源 | 从公网 CDN 加载 Bootstrap，未加完整性校验 | ⚪ 已知风险，已接受（见第 10 节） |

### 7.2 性能

- 活动列表**必须分页**，单页 10 条。
- 列表查询走索引（状态 + 开始时间）。
- 目标：单次页面响应 < 500ms（校内网、百级并发）。

### 7.3 可用性

- 表单校验失败保留已填内容。
- 所有拒绝操作给出**具体原因**，不使用「操作失败」这类无信息量的提示。
- 错误页提供回到首页 / 登录的出口。

### 7.4 兼容性

- 响应式，优先保障手机浏览器（学生主要在手机上使用）。
- 支持近两年主流浏览器。

### 7.5 数据

- 时间统一以 **UTC** 存储，展示时转本地时区。
- 所有时间边界判断**以服务端时间为准**，前端传入的时间一律不可信。
- 数据库：MVP 用 SQLite 单文件，表结构按 MySQL 8 口径设计，便于后续迁移。

## 9. 非目标

以下内容**明确不做**，列出来是为了避免范围蔓延。

| 不做的事 | 原因 |
| --- | --- |

| 活动二维码海报 | 依赖二维码生成与图片合成，属于运营增强 |

## 10. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **报名超卖** | 最高。直接导致活动执行失控，且是这类系统的经典缺陷 | 数据库层原子扣减 + 唯一索引兜底；M3 用并发测试验证 |
| **名单锁定规则引发反感** | 中。学生可能认为「不让我取消」不合理 | 在还能取消时就明确显示截止时刻；锁定窗口可在配置中调整 |
| **会话保护导致频繁掉线** | 中。移动网络下 IP 变化会触发重新登录 | 当前使用强会话保护；若掉线过于频繁，可降级为弱保护并对敏感操作单独要求重新验证 |
| **审核成为瓶颈** | 中。所有社团活动都要等管理员，可能拖慢发布 | MVP 先保证审核存在；如需提速，可给可信社团开「直接发布」白名单 |
| **前端资源依赖 CDN** | 低。校外网络或 CDN 故障会导致样式丢失，且未加完整性校验 | **已接受**：本项目为课程作业，不自托管。若将来真实部署上线，再改为本地静态资源 |
| **数据量增长** | 低。SQLite 在单校区规模下足够 | 表结构按 MySQL 口径设计，迁移成本可控 |

| 上座率 | 报名人数 ÷ 人数上限 |
| 归属权校验 | 确认当前用户是否为该资源的创建者（或具备管理员权限） |
| 会话（Session） | 服务端记住「你是谁」的机制，通过签名的 Cookie 在浏览器与服务器之间传递 |
| CSRF | 跨站请求伪造：第三方站点冒用你的登录态发起请求 |
