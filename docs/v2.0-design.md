# 校园活动管理系统 V2.0 — 设计方案

> 版本：v2.0　最后更新：2026-10-11
>
> **需求依据**：《实验2-需求分析.md》（40 条访谈议题 → FR / BR / TC / DEC）。
> 本文档是**实现层面**的依据：角色与权限、状态机、数据模型、核心机制的做法、
> 接口变化、迁移方案。业务规则有歧义时，以需求分析文档第六章「业务规则」为准。
>
> V1.0 的技术细节见 [`mvp-design.md`](./mvp-design.md)（历史文档，已被本文档取代）。

## 1. V2.0 相对 V1.0 的变化一览

| 维度 | V1.0 | V2.0 |
| --- | --- | --- |
| 角色 | 学生 / 社团 / 校级管理员 | 学生 / **活动组织教师** / 系统管理员 |
| 活动审核 | 社团提交 → 管理员通过 / 驳回 | **取消**：教师创建即发布；管理员改为事后**下线 / 恢复** |
| 满员处理 | 报名被拒（"名额已满"） | **候补队列**：排队等位，先到先得，名额空出自动递补 |
| 报名审核 | 无 | 需审核的活动由**组织教师逐人确认**；通过 ≠ 正式（看当时余位） |
| 报名状态 | 已报名 / 已取消（两态） | 待审核 / 正式 / 候补 / 已拒绝 / 已取消（**五态**） |
| 管理员边界 | 对活动近似"全权" | 只做平台级状态处理：账号停用 / 恢复、活动下线 / 恢复 |

**保留的 V1.0 基础能力**：浏览与筛选、报名、名单与签到（含 6 位签到码）、
分类管理、账号管理、密码找回、登录失败锁定等——均按原样保留。

## 2. 角色与权限（实现版）

| 功能 | 学生 | 组织教师 | 系统管理员 |
| --- | :---: | :---: | :---: |
| 浏览已发布活动 / 详情 | ✓ | ✓ | ✓ |
| 报名 / 加候补 / 取消本人报名 | ✓（仅本人） | ✗ | ✗ |
| 创建 / 发布 / 修改活动 | ✗ | ✓（仅本人负责） | ✗ |
| 设置上限 / 资格 / 审核开关 | ✗ | ✓（仅本人活动） | ✗ |
| 审核报名、管理名单与签到 | ✗ | ✓（仅本人活动） | ✗ |
| 查看平台全部活动 | ✗ | ✗（仅本人） | ✓ |
| 活动下线 / 恢复 | ✗ | ✗ | ✓ |
| 查看 / 停用 / 恢复账号 | ✗ | ✗ | ✓ |

实现要点：

* 权限一律在**服务端**校验，装饰器两道：`role_required`（角色）、
  `owner_required`（归属权）。**管理员不再默认放行** `owner_required`——
  需求分析 3.1 明确「管理员不代替教师编辑活动内容、不处理具体报名」。
* 学生侧的写操作只作用于 `current_user`，路由上不存在"操作别人报名"的参数，
  结构上就没有越权的可能。

## 3. 状态机

### 3.1 活动状态（六态）

```
DRAFT ──发布──> PUBLISHED ──时间到──> ONGOING ──时间到──> FINISHED
                  │  ↑                                   │
                  │  └──────恢复（管理员）──────────────┐  │
                  └──下线（管理员）──> OFFLINE ──────────┘  │
                                                            │
DRAFT / PUBLISHED / ONGOING ──取消（组织教师）──> CANCELED <─┘（不可逆）
```

* 时间推进（`PUBLISHED → ONGOING → FINISHED`）在每次请求时现算，不引入调度器；
* `OFFLINE` **不参与**时间推进，恢复时按时间重新定位（可能直接落到 ONGOING/FINISHED）；
* `CANCELED` 与 `FINISHED` 为只读；`ONGOING` 起活动信息整体锁定。

### 3.2 报名状态（五态，需求分析第七章）

```
[*] ──报名（无需审核·有余位）──> 正式 CONFIRMED
[*] ──报名（无需审核·满员）────> 候补 WAITLISTED
[*] ──报名（需审核）──────────> 待审核 PENDING
待审核 ──通过（有余位）──> 正式
待审核 ──通过（无余位）──> 候补（记录"通过时刻"为进入候补时间）
待审核 ──拒绝───────> 已拒绝 REJECTED（终态，不进候补）
待审核 ──撤销/候补──退出/正式──取消──> 已取消 CANCELED（终态）
候补 ──名额空出·系统自动递补──> 正式
```

* 「待审核 / 正式 / 候补」= **有效报名**：同一学生对同一活动最多一条（唯一索引兜底）；
* 已拒绝 / 已取消之后可重新报名，**按新的时间重新排队**（DEC-3，复用同一条记录）。

## 4. 数据模型

### 4.1 变更点

| 表 | 变更 |
| --- | --- |
| `user` | `role` 取值：`CLUB` → `TEACHER`；`club_name` 语义放宽为「所属组织」 |
| `activity` | 新增 `requires_review`（是否需审核）、`qualification`（参加资格说明）；删除审核流字段的使用（`approved_by` / `approved_at` / `reject_reason` 保留在旧库中不再读写） |
| `enrollment` | 新增 `waitlisted_at`（进入候补时间，**排序唯一依据**）、`reviewed_at` / `reviewed_by`（审核时刻与操作人）；`status` 扩展为五态 |
| `audit_log` | 记录活动级事件：`PUBLISH` / `OFFLINE` / `RESTORE` / `CANCEL`（下线原因在这里，供「处理标记」展示） |

### 4.2 迁移（V1.0 → V2.0）

命令行：`flask upgrade-v2`（幂等，可重复执行）。线上由 `deploy.py` 启动时自动执行。

取值翻译规则：

| 位置 | 旧值 | 新值 | 理由 |
| --- | --- | --- | --- |
| `user.role` | `CLUB` | `TEACHER` | 角色改名，账号与数据不动 |
| `activity.status` | `PENDING` | `PUBLISHED` | 审核流取消，「等着批」视为已发布 |
| `activity.status` | `REJECTED` | `DRAFT` | 退回草稿，由教师修改后自行发布 |
| `enrollment.status` | `ENROLLED` | `CONFIRMED` | V2.0 的「正式」 |

**数据不重建**：账号、活动、报名记录一条不少，只补列、翻译取值。
迁移前的库建议留存备份（本地已备份为 `instance/campus.db.bak-before-v2`）。

## 5. 核心机制的实现

### 5.1 候补队列（FR-4）

* **排队**：满员时报名直接写入 `WAITLISTED`，并记录 `waitlisted_at`；
* **位置**：不落库，查询时按 `(waitlisted_at, id)` 现算——「退出后自动前移」
  （BR-7）因此天然成立，**系统里不存在任何调整顺序的入口**；
* **递补**：名额空出（正式取消、教师调大上限）时，`promote_waitlist` 把队首
  逐位转正式，直到"又满了"或"没人等"为止；
* **票数语义**：候补**不占名额**，`activity.enrolled_count` 的口径始终是"正式人数"。

### 5.2 容量硬约束（BR-1）与并发

所有会让正式人数 +1 的路径（直接报名、审核通过、候补递补）都走**同一条
原子条件 UPDATE**：

```sql
UPDATE activity SET enrolled_count = enrolled_count + 1
WHERE id = :id AND status = 'PUBLISHED'
  AND enrolled_count < capacity
  -- 直接报名还会多一个 enroll_deadline > :now
```

判断与扣减压在同一条语句里完成，不存在"先查再改"的竞态窗口；
抢不到名额时按业务分流：报名 → 候补，审核通过 → 候补，递补 → 停止。

取消（释放名额）与递补（占用名额）在**同一个事务**内完成，
不存在"名额已空出但还没递给队首"的空窗期。

### 5.3 报名审核（FR-6）

* 审核动作只有组织教师本人可做（`owner_required`，管理员也会被 403）；
* 通过与余位的衔接就发生在 `_take_slot` 的成功/失败上（见 5.2），
  "通过 ≠ 正式"不是一句提示语，而是结构性保证；
* 拒绝是终态，不进入候补——不允许"先拒了再悄悄排队"。

### 5.4 名单锁定与"随时退出"的取舍

* 「正式」报名的取消有锁定：距截止不足 24 小时、截止后、活动开始后、已签到，
  均不可取消（V1.0 既有规则，保留）；
* 「候补退出」「待审核撤销」**不受锁定**（FR-4.4 明确"随时退出"）——
  这两种状态不占名额，退出没有成本。

## 6. 接口变化

| 变化 | 明细 |
| --- | --- |
| 移除 | `POST /activities/<id>/submit`、`/withdraw`、`/approve`、`/reject`（活动审核流）；`GET /admin/audit`（审核中心页） |
| 新增 | `POST /activities/<id>/publish`（草稿发布）；`POST /activities/<id>/enrollments/<uid>/approve`、`/reject`（报名审核）；`POST /admin/activities/<id>/offline`、`/restore`（活动监督） |
| 更名 | `/club/enrollments` → `/teacher/enrollments`；`/club/stats` → `/teacher/stats`；`main.club_home` → `main.teacher_home`（`/teacher/`） |
| 复用 | 报名 `POST /activities/<id>/enroll`：结果可能是 正式 / 候补 / 待审核三种，提示语由业务层返回 |
