# 校园活动管理系统 V3.0 — 设计方案

> 版本：v3.0　最后更新：2026-10-25
>
> **需求依据**：《实验3-需求分析.md》——基于 V2.0 平台模拟运行数据提出的 12 条
> 数据驱动需求（DR-1 ~ DR-12）。
> **基本原则：只加不删。** V2.0 的全部能力（候补队列、报名审核、活动监督、
> 报名五态、签到、统计、邮件、公告、开放注册）一条都没有移除，V3.0 是在它们
> 之上补「三个闭环、透明度、体验与决策支持」。

## 2. 数据模型变更（仅一处）

| 表 | 变更 | 理由 |
| --- | --- | --- |
| `enrollment` | 新增 `promoted_at DATETIME` | 记录「候补 → 正式」的时刻。转正率的分母是「曾进入候补的记录数」，分子是「其中真的转正的记录数」——只靠 `status` 分不出「直接报名转正式」和「候补转正」。 |

配套的行为调整：

* `waitlisted_at` **不再在退出候补时清空**（V3.0 起保留为「候补历史」）。
  队列查询只看 `status == WAITLISTED`，不会被误当成还在排队。
* `_write_application` 重新报名时会把 `promoted_at` 一并复位（新一轮从零开始）。
* `migrations.schema_needs_upgrade()` 改为**逐表逐列核对** `NEW_COLUMNS`：
  V2.0 的库缺 `promoted_at` 也会被识别并自动补列，迁移仍然幂等。

## 3. 核心机制说明

### 3.1 通知（DR-3）为什么复用邮件表

V2.0 已经有完整的站内邮件：`Message` + `MessageRecipient`（已读时间记在收件人上），
未读角标、已读状态、详情页全都能用。系统通知只是「`sender_id` 为空的消息」——
收件箱里显示成「系统」，其余逻辑零改动。

**同事务写入**：`notify_user` 不提交，由触发它的状态变更（转正 / 审核）一起提交。
这样不会出现「状态改了但没通知」或「通知了但状态没改」。

### 3.2 候补转正率的口径（DR-4）

```
候补总数 = 该活动 waitlisted_at 非空的报名记录数（含已转正、仍在等、已退出）
转正数   = 其中 promoted_at 非空的记录数
转正率   = 转正数 / 候补总数
```

样本 < 3 时不报比例（显示「暂无参考」）——1/1 = 100% 只会误导。
机会标签：≥50% 机会较大 / ≥20% 有机会 / <20% 机会较小。

### 3.3 时间冲突（DR-11）

只查「本人 `CONFIRMED` 且活动可见」的记录：

* **时间区间重叠**（`other.start < mine.end AND other.end > mine.start`）→ 冲突；
* **本地日期相同**（同一天）→ 也算冲突，但提示语区分「时间重叠 / 同一天」。

不强制拦截：命中后返回确认页，用户点「仍然报名」（表单带 `confirm=1`）才真正提交。

### 3.4 热度与容量参考（DR-12）

* 热度只看**填充率 + 余位**（可解释、可复算，不假设历史数据）：
  已满员 / 即将满员（≥80%）/ 较热（≥50%）/ 一般。
* 容量参考用同类活动的「正式人数 + 当前候补人数」近似真实需求，
  给出均值 ±20% 的区间；样本 < 2 场活动时不给建议。

### 3.5 运行指标（DR-5）的边界

纯内存环形缓冲（最近 500 次报名请求），进程重启清零、不落库。
页面上明确写出这个局限，不冒充持久化监控系统。慢请求阈值 300ms，
与需求分析附录 B 的口径一致。

## 4. 演示数据（`flask seed-demo --reset`，13 活动 / 18 账号）

新增一场 **「摄影后期工作坊」**（满员 6/6）：

* 其中 2 人是「候补转正」进来的（`promoted_at` 有值），2 人还在候补 →
  转正率 50%，详情页显示「机会较大 · 转正率 50%」（DR-4）；
* 与「手机摄影技巧分享会」同一天 → 用 `20230101` 报名时会走一次
  时间冲突二次确认（DR-11）。

另外给 `20230101` 预置两条系统通知（候补转正、审核通过），登录后右上角
邮件角标即可看到（DR-3）。

推荐走查顺序：

1. `20230101` 登录 → 活动广场筛选「已满 · 可候补」→ 打开「摄影后期工作坊」
   → 看候补机会参考 → 点「加入候补队列」→ 冲突确认 → 仍然报名 → 成为候补第 3 位；
2. 同账号进「邮件」→ 看两条系统通知；
3. `club001` 登录 → 发布活动页 → 看结构化地点 + 同类活动容量参考；
4. `admin` 登录 → 管理后台 →「运行指标」看 P95 / 慢请求占比。

## 6. 与 V2.0 的关系

* **没有删除任何功能**：候补、审核、监督、签到、统计、邮件、公告、注册全部保留；
* 唯一的行为变化是「重复提交的提示语」从「你已经报名过」改成「你已报名成功」，
  以及 `waitlisted_at` 退出候补后不再清空（为了让转正率算得准）；
* 数据库升级是**加列 + 幂等迁移**，不需要重建库，V2.0 数据原样可用。
